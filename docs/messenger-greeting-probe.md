# Приветствие в звонках мессенджеров — эксперимент

Тестовая ветка `feat/messenger-greeting-probe`, приложение `0.29.5-msgr-test`.
Функция по умолчанию выключена. В экране «Запись звонков в мессенджерах» появился
отдельный переключатель «Принимать звонки и говорить приветствие».

## Поведение

- Только выбранные приложения: Telegram, WhatsApp, WhatsApp Business.
- Только свежие входящие голосовые `Notification.CallStyle` с явным `answerIntent`.
  Исходящие, видео, уведомления при переподключении слушателя и уже принятые звонки
  не инициируют автоответ.
- Используется общее приветствие автоответчика: свой файл или TTS, выбранный язык,
  затем сигнал. Максимальная длина — 120 секунд.
- Shell-хост получает PCM по отдельному сокету, проверяет UID клиента, регистрирует
  временную `AudioPolicy` с `MIX_ROLE_INJECTOR` и `RULE_MATCH_UID` мессенджера.
  Подготовка происходит **до** отправки действия принятия звонка.
- Приветствие заменяет входной звук этого приложения. После воспроизведения политика
  снимается; предполагается возврат к микрофону. Фактический возврат проверяет probe.
- Запись обеих сторон использует прежнюю независимую политику и прежний сокет.
  Переключатель записи можно включать отдельно от приветствия.
- Отключение функции/разрыв IPC отменяет подачу звука. Есть ограничения длительности
  и ожидания подключения; постоянного опроса системы между звонками нет.
- Звонок после приветствия остаётся активным: можно говорить или завершить его вручную.
  Автоматический отбой/приём сообщения на заданное время в этом эксперименте не добавлены.

## Проверка без звонка

Запускать под shell UID 2000, **не под root**:

```sh
apk=$(pm path com.davnozdu.autoresponder | sed 's/package://')
CLASSPATH="$apk" app_process /system/bin com.davnozdu.autoresponder.msgrec.MsgrInjectionProbe
```

Проверка подаёт 997 Гц в виртуальный вход и читает его через новый
`AudioRecord(VOICE_COMMUNICATION)` того же shell UID. Печатает амплитуду, долю энергии
контрольного тона и PASS/ошибку. Затем снимает политику и проверяет, что тот же
`AudioRecord` читает данные и маршрутизирован обратно к устройству микрофона.
Звонки не принимаются, аудиофайлы не сохраняются.

Этот тест подтверждает механизм Android. Он **не доказывает** передачу звука
удалённому абоненту конкретного мессенджера.

## Живой звонок

1. После обновления убедиться, что `msgr-host.log` содержит `injection host ready`.
2. Включить приветствие и выбрать тестируемый мессенджер; включить запись для проверки.
3. Позвонить на этот телефон с другого аккаунта голосовым вызовом. Не отвечать вручную.
4. Проверить автоматическое принятие, слышимость полного приветствия и сигнала у
   звонящего. После сигнала произнести фразу с обеих сторон, проверить возврат микрофона.
5. Завершить звонок. Проверить обе стороны WAV и появление записи в журнале.
6. Проверить повторный вызов, ручной ответ до автоответа, отмену входящего вызова,
   выключение функции. Проверить отсутствие автоответа на исходящие и видео.

События приложения: `MSGR AM:`. Shell-хост: `msgrec inject`.

Механизм основан на API AOSP:
`frameworks/base/media/java/android/media/audiopolicy/AudioPolicy.java`,
`AudioMixingRule.java`, пример `platform/development/samples/VirtualDeviceManager/host/src/`
`com/example/android/vdmdemo/host/AudioInjector.java`.
